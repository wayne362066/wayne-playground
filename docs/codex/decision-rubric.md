# 判斷力 Rubric

這份 rubric 把「完成、升級、詢問、換路」轉成可觀察判準。若證據不符合完成門檻，狀態只能是「未完成」「未驗證」或「阻塞」，不能用語氣補足證據。

## 狀態定義

| 狀態 | 必要訊號 | 動作 | 停止條件 |
| --- | --- | --- | --- |
| 完成 | 目標與範圍明確；所有授權變更已落檔；必要驗證全部通過，命令有 exit code、人工檢查有步驟與觀察結果；read-back／引用檢查通過；未解風險不影響承諾目標 | 回報完成，列檔案／行號、驗證與剩餘非阻塞風險 | 不得因時間、token 或「看起來合理」提前完成 |
| 部分完成 | 部分切片符合門檻，但仍有明確未完成項 | 回報已完成切片與剩餘項，不能標整體完成 | 依剩餘項繼續或交接 |
| 未驗證 | 內容已改，但必要命令因環境／權限／依賴未能執行，或替代驗證不等價 | 標示具體阻塞與已做替代檢查 | 阻塞解除前不宣稱通過 |
| 阻塞 | 缺少使用者選擇、外部權限、不可取得的必要資料，或同策略已按規則失敗兩次且無安全換路 | 停止猜測，提出最小問題或交接封包 | 等待明確輸入／外部狀態改變 |

必要驗證失敗時是「未完成」；可在已授權範圍內修正，無安全解法才標阻塞。exit 0 但相關測試被 skip，也不能當該行為通過；無關的既有 skip 不阻塞本次範圍，但須說明不相關理由。一般批准不取消必要驗證；改驗收範圍需使用者明確決定，原失敗紀錄仍保留。

## 何時升級模型或取得第二意見

### 觸發條件

- 測試、實際檔案或架構圖與目前假設直接矛盾。
- 同一推理錯誤、幻覺命令或需求誤判已被指出一次；再次處理前不得沿用原假設。
- 需要跨 backend／frontend／Docker 邊界的設計決策，且一個錯誤會改變三個以上模組或資料流。
- 核心治理文件的決策條款（如完成、權限、調度、Git gate）修改後，需要不帶主 thread history 的獨立審查；純文字／路徑修正按 maintenance 的受影響範圍檢查。
- 安全、資料不可逆、權限、正式部署或使用者資料風險高於本地測試可覆蓋範圍。

### 動作與停止

1. 先把目標、範圍、假設、已試方法、確切錯誤／exit code、已驗證結果與希望裁決的問題寫成升級封包。
2. 按 `dispatch-playbook.md` 的能力與授權檢核派工：獨立審查須不帶主 thread history；也接受使用者另開、不含原對話歷史的新 session。記錄實際工具／參數或獨立 session 來源，不填未使用的參數。無可用方式才留下審查 Prompt 並標未完成；模型／effort 選擇不繞過當前工具限制。
3. 主模型直接核對第二意見提到的高槓桿檔案與行號；第二意見不是驗收替代品。
4. 第二意見仍無法在證據上決定時，停止改動並交接／詢問，不再以同一假設重試。

### 正例與反例

正例：`make test` 因 Docker socket 被拒絕，主機 PHP 測試通過；把它分類為容器路徑未驗證，並明確說明兩個入口都只使用隔離的 SQLite／array 測試後端，不代表 PostgreSQL／Redis 整合通過。

反例：主機 unit／feature 測試通過，就把 Docker Compose、PostgreSQL、Redis 依賴也寫成「全部通過」。

## 何時真正完成

完成判斷要同時滿足四個問題：

1. 做了使用者要求的事，沒有偷偷改變範圍。
2. 必要檔案存在且 read-back 內容與意圖一致。
3. 必要驗證全部通過；只明示失敗／未驗證，不算達標。判準是本次承諾的行為，不只是命令結束。
4. 沒有 placeholder、虛構工具、斷裂引用、未授權副作用或未處理的高風險假設。

功能任務另有 Git gate：功能必須在符合 `<type>/<english-kebab-case-summary>` 的獨立分支；Codex 建立的一般 commit 必須符合 `<type>(<scope>):<中文摘要>`；沒有本次 SHA／remote／ref 的使用者批准就只能回報「待推送審核」。使用者確認確切功能 SHA review 完成後，Codex 只能自主合併到 `develop`；合併後的 `develop` push 仍須以新 SHA 送審。遠端 `develop` 就緒後狀態是「待使用者合併 main」，Codex 不得自行 merge／push `main`。完整狀態與證據見 `git-review-release-protocol.md`。

### 正例與反例

正例：治理任務新增文件後，逐檔 read-back，`rg` 解析引用皆存在，文件檢查命令 exit 0；因 Docker 被拒絕的產品測試不屬於本次治理變更，仍列為環境未確認而不隱藏。

正例：功能在 `feat/minecraft-module` 完成並通過測試，向使用者提供 SHA、目標 ref 與 diff 後停在「待推送審核」；review 完成後自主合併到 `develop`，再以新的 `develop` SHA 取得 push 批准；最後停在「待使用者合併 main」。

反例：只看到 `apply_patch` 成功，沒有重新讀檔、路徑檢查或驗證，就回報「制度已完成」。

反例：使用者曾說「可以」，HEAD 後來又新增 commit，仍沿用舊批准 push；或 Codex 因 `develop` 已通過測試就自行 merge／push `main`。

## 何時必須詢問使用者

### 觸發條件

- 兩個合理方案會造成不同公開 API、資料格式、部署成本或使用者體驗，repo／測試沒有偏好證據。
- 需要刪資料、重建資料庫、覆蓋既有未追蹤檔、推送／建立 PR、安裝插件或使用外部帳號權限，而使用者沒有明確授權。
- 每一次 push 前都要取得綁定完整 SHA／remote／ref 的單次使用者批准；每一次發佈前都要取得綁定候選 SHA／目標／方式的獨立批准。
- 功能合併策略沒有 repo 明文慣例、出現 conflict、來源／`develop` SHA 不一致，或不確定 review 是否已完成。
- 需求互相衝突，且不能用更具體的規則、既有測試或 README 解決。
- 驗證 oracle 缺失，例如想判定 UI 視覺是否符合偏好、正式服務是否安全，卻只有本地開發配置。
- 對需求、範圍、功能分類、Git 基底／分支、remote／ref、工具結果、權限、審核狀態或命令效果做一次針對性查證後仍不確定。

### 動作與停止

- 先查本地證據；可查證的環境事實不向使用者提問。
- 問最小且有選項影響的問題，說明目前已知、兩個選項及不選的後果；等待答案前不做高風險改動。
- 若只是低風險、可回復且不改變意圖的格式選擇，採 repo 既有慣例並在回報中說明假設，不必詢問。
- 對 push／發佈不採用默認批准：沒有精確批准就停在對應待審核狀態；SHA、目標或參數改變時重新詢問。
- Codex 合併功能的唯一目標是 `develop`；`develop` 到正式 `main` 不詢問代執行許可，而是提供 SHA／diff／驗證後停止，由使用者親自合併。

### 正例與反例

正例：要把 Docker 測試改成新增 host fallback target，會改變專案介面；先詢問是否要擴大 Makefile 範圍，而非擅自改業務／工具。

正例：已確認功能與測試，但不知道使用者要推到 `origin` 還是另一個 remote；提供目前 remote 證據並詢問，未回答前不 push。

反例：README 已明確說新增模組要跑 `cd frontend && npm run build`，卻因不確定工作目錄而停下詢問；這可以從 `frontend/package.json` 查出。

反例：不確定發佈是建立 tag 還是部署 production，便自行選擇其中一個並聲稱使用者已批准。

## 何時換路而不是重試

### 觸發條件

- 相同命令、相同權限、相同輸入已失敗兩次。
- 錯誤類型已清楚是環境／工具問題，而不是被測程式問題。
- 目前工具輸出開始污染 context（依賴／二進位／長 log），可以改用 `rg`、摘要、檔案落檔或較窄的查詢。
- 替代檢查雖可前進，但與原驗收不等價。

### 動作與停止

- 變更至少一個維度：分類、工具、輸入範圍、執行位置、隔離方式或解法；同時記錄不等價之處。
- 環境錯誤：只調整條件後再試一次；仍失敗就採已存在替代命令或交接。
- 推理錯誤：不再重跑相同命令，改讀證據或取得第二意見。
- 替代檢查不能支持承諾目標時，保持「未驗證」，停止擴張。
- 等待工具逾時不計入兩次失敗；按 `dispatch-playbook.md` 的等待生命週期處理，不因兩次輪詢無結果就關閉仍在執行的 agent。

### 正例與反例

正例：Docker socket 連不上後改跑已存在的 `cd backend && php artisan test` 與 `cd frontend && npm run build`，回報主機測試不能替代容器路徑，且兩個 backend 測試入口都不涵蓋 PostgreSQL／Redis 整合。

反例：反覆執行同一個 `make test`，只因想取得不同結果，最後把最後一次未成功的命令省略。

## 任務類型的最低驗證

任何屬於功能的 backend、frontend 或跨層任務，除下表驗證外，還必須符合 `git-review-release-protocol.md`：獨立分支、每次 push 單次審核、review 後只合併 `develop`、`main` 由使用者親自合併。缺少任一 gate 時可完成本地實作，但不能宣稱已整合或已發佈。

| 任務類型 | 最低完成條件 | 最低驗證 | 明確不能宣稱 |
| --- | --- | --- | --- |
| 治理／文件 | 目標文件已落檔，引用與路由可達，無矛盾或未替換標記 | 每檔 read-back；`test -s`；對引用路徑做 `test -e`／`rg`；有 Git 基線才跑 `git diff --check` | 不能因文件看起來合理就宣稱模型／工具在所有 session 都可用 |
| backend | 相關程式與測試一致，API／資料邊界未破壞 | 優先 `make test`；若 Docker 阻塞，`cd backend && php artisan test` 只能標 host 測試通過、容器路徑未驗證；兩者都必須由測試 guard 確認使用 SQLite `:memory:` | 不能把任一 PHPUnit 入口寫成 PostgreSQL／Redis 整合通過 |
| frontend | 相關元件與路由可建置 | `cd frontend && npm run build`；若有明確 lint／type-check script 才執行，沒有就標未提供 | 不能把 build 通過說成瀏覽器視覺／互動全通過 |
| 跨層／Docker | backend、frontend、配置與資料流都在範圍內 | backend 與 frontend 最低驗證都跑；服務可用時再跑 Compose／健康端點；任一未驗證須列出 | 不能只測一層就宣稱 end-to-end 完成 |
| 研究／調查 | 問題、時間範圍與來源邊界固定，結論可追溯 | 對每個關鍵結論保留來源／路徑／日期與反例檢查；長報告落檔 | 不能把推測或未查證的外部能力寫成事實 |
| 審查 | 審查目標只讀，發現能定位且沒有漏讀核心目標檔 | 任務要求獨立審查時，記錄不繼承 history 的實際派工方式或独立新 session 來源；逐一讀目標檔；回報嚴重度、路徑／行號、理由與驗證；只可寫派工明確授權的報告路徑 | 「沒有發現」不代表通過測試或安全，只代表指定範圍未找到問題 |

上表是最低入口，不是所有行為的充分驗證。開始實作時，將使用者驗收條件對到現有測試或可重現的人工步驟；下列情境增加對應檢查，不自動新增框架或連正式資料庫：

- UI／路由／互動改變：除了 build，實跑受影響流程，記錄操作、預期與實際結果；例如對戰流程只驗本次受影響的 ready／重連／rematch。環境不能實跑時，互動仍是未驗證。
- 權限／API 改變：包含允許與拒絕情境，不以登入成功代替未授權存取檢查。
- PostgreSQL／Redis 專屬行為改變：隔離的 SQLite／array 測試不夠；需要已授權且隔離的對應服務驗證，否則該目標未驗證。不得移除 `backend/tests/TestCase.php` 的防護去連應用資料庫。

正例：只改文件引用，產品測試不是必要項；改 PostgreSQL 欄位註解，`MigrationColumnCommentTest` 在 SQLite 被 skip，則註解效果仍未驗證。反例：對戰按鈕 build 通過，就把多人互動流程標完成。

## 不宜可靠制度化的判斷

以下事項目前沒有本 repo 的客觀 oracle，制度只能要求停下並說明，不應假裝有固定答案：

- `hero.png`、Vue UI 或模組文案是否符合個人審美；需要使用者或視覺 QA。
- 正式部署、網路暴露、備份還原與安全風險；目前 README 明確是開發 compose，且沒有 CI／production oracle。
- 外部 connector 的登入、權限、資料完整性與第三方服務目前狀態。
- 使用者未指定的產品取捨，例如 API 相容性、資料遷移策略、模組排序或錯誤訊息語氣。
- 模型的實際品質、context 上限、並行容量與服務可用性；只能記錄當前工具回應，不能從一次成功泛化。

遇到以上事項，動作是列出已知證據、未知點、可逆選項與需要的使用者決策；停止條件是選擇或可靠 oracle 出現前不做不可逆承諾。

## Rubric 自查

收尾前逐項回答：

- 是否有目標／範圍／禁止事項／驗收證據？
- 每一個「通過」是否都有命令與 exit code，或可重現的人工步驟與觀察結果？
- 是否把替代檢查、環境阻塞、推測與真正通過分開？
- 是否因兩次失敗而換路或升級，而非第三次原樣重試？
- 是否有任何選擇其實應由使用者決定？
- 是否有任何制度規則只是一次性直覺，應留在交接而非升格？

任一答案不利時，狀態至少是「未完成／未驗證」，直到補證據或取得決策。
